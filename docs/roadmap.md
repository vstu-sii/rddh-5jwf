# Роадмап и скоуп MVP

Роадмап отделяет «сейчас» от «потом». Всё, что не записано в раздел «MVP», в MVP не входит. Всё, что записано в «Не-скоуп», в MVP не попадёт без правки этого файла через PR (правила — в конце).

Источники: [use cases](use-cases/README.md), [PRD](prd.md), [критерии успеха](quality/success-criteria.md), [C4](architecture/README.md), [ADR](adr/README.md).

## 1. Что строим к Demo Day

Сотрудник загружает чек (фото или PDF), за секунды видит распознанные поля, категорию и вердикт политики, отправляет расход, следит за статусом и получает понятную причину решения. Бухгалтер разбирает только спорные расходы, остальные утверждает пачкой и формирует реестр на выплату без ручной сводки.

**Сценарий демонстрации** (сквозной, на обоих входах): Анна фотографирует чек языковой школы и загружает PDF фитнес-клуба → оба превращаются в расходы → один уходит как спорный → Ирина-бухгалтер разбирает спорный с причиной, утверждает остальные пачкой → формирует реестр, сумма сходится → Анна видит «В реестре» с историей событий.

## 2. MVP: что входит

Скоуп выведен из use cases: один UC — один пункт, глубина указана явно.

| UC | В MVP | Граница глубины (что именно делаем) |
| --- | --- | --- |
| UC-01 Загрузить чек | **Да** | Фото и PDF как равноправные входы; QR → ФНС только если доступ получен (иначе текст/OCR); пересъёмка; «Чека нет»; дубли; деградация |
| UC-02 Проверить и отправить | **Да** | Правка полей, вердикт политики по позициям до отправки, комментарий, спорный/неспорный, удаление неподанного |
| UC-03 Статус и причина | **Да** | Список, карточка, журнал событий с актором, причина; обновление опросом |
| UC-04 Срок и неподанные | **Да, урезанно** | Баннер периода и блок «Ждут отправки» внутри приложения; без внешних напоминаний |
| UC-05 Спорные расходы | **Да** | Очередь, карточка с оригиналом, решение «всё / частично / отклонить» с обязательной причиной и её типом |
| UC-06 Пачка | **Да** | Утверждение неспорных пачкой, атомарно; без автоодобрения |
| UC-07 Реестр | **Да** | Реестр за период по решениям, контроль суммы, XLSX, «Передать на выплату», «Отметить выплаченным» |

Сквозные условия MVP (из Delivery и Quality):

- Одна пилотная компания, один набор политики (справочник категорий с признаком «компенсируется»), заведённый командой.
- Два актора: сотрудник и бухгалтер, вход по логину и паролю.
- Категоризация: правила + локальная LLM (Qwen2.5-7B) за адаптером `categorize()`, облачный резерв и правила как деградация ([ADR-0003](adr/0003-acl-adapters-for-external-systems.md), [model-candidates](model-candidates.md)). Без RAG и агента ([research](research.md), раздел 4).
- Распознавание асинхронное, обычно до 5 с ([ADR-0001](adr/0001-async-recognition-pipeline.md)).
- Данные — только через `expense_store` ([ADR-0002](adr/0002-single-data-owner.md)).
- Окружение: `compose.dev.yml` поднимает все контейнеры C4 одной командой.

## 3. Не-скоуп (явно)

Каждый пункт ниже сознательно не делаем в MVP. «Когда вернуться» — условие, а не дата.

| Не делаем | Почему не сейчас | Вернуться, когда |
| --- | --- | --- |
| Импорт банковских выписок (CSV/XLSX), сверка «чек ↔ операция» | Это тема из ранних версий проекта (`research.md`, шапка README); в PRD и C4 её нет. Сегмент — компенсация расходов сотрудников | Если появится сегмент «учёт расходов», отдельная гипотеза и новый PRD |
| Согласование руководителем | Согласует бухгалтер; нового актора пришлось бы закладывать в C4 (`stableDependencies`) | Пилотная компания потребует двухступенчатого согласования |
| Интерфейс HR для политики компенсации | Политика — справочник, заводится командой; редактор политики — отдельный продукт | Политика у пилотной компании меняется чаще раза в квартал |
| Автоматический расчёт и проверка лимитов (`monthly_limit_kopecks`) | Поле в схеме есть, правило — нет; не хватает согласованных лимитов от компании | Получены лимиты пилотной компании |
| Push, email, мессенджер-напоминания о сроке; поиск «забытых» чеков в галерее или почте | Нужен сервис уведомлений, которого нет в C4; боль 4 закрываем частично (UC-04) | После Demo Day; тогда новый контейнер и ADR |
| Подсказка «компенсируется ли» **до покупки** (боль 3 в полном виде) | MVP показывает вердикт политики после загрузки чека, до отправки; до покупки — другой сценарий | Если H3 в `hypotheses.md` подтвердится интервью |
| Автоодобрение без бухгалтера | Деньги и налоговое основание; решение всегда у человека | Q-01 стабильно ≤ 5% на реальных данных и согласие компании |
| Обучение на решениях бухгалтера (алиасы, правила, дообучение) | Нужны данные и контроль качества; MVP работает по справочнику | Накоплено ≥ несколько сотен подтверждённых решений |
| RAG по документам политики; агентный контур | Решение AI Engineer: прямые промпты + правила ([research.md](research.md)) | Большой справочник продавцов или многошаговые сценарии |
| Интеграции с 1С, зарплатным контуром, банком; фактические выплаты | Реестр — файл; выплата происходит вне системы | Пилот требует автоматической передачи реестра |
| Корпоративный SSO, самостоятельная регистрация, управление пользователями | Учётные записи заводит команда | После пилота |
| Нативные приложения, офлайн-режим, очередь отправки на устройстве | PWA; без интернета загрузка не выполняется | После Demo Day |
| Приём чеков из почты, «поделиться в приложение», массовая загрузка пачкой | Только выбор файла и камера | Если H2 подтвердится |
| Валютные расходы, рукописные чеки, многостраничные PDF-выписки, доходы | Вне сегмента и вне golden dataset | Расширение сегмента |
| Отмена и корректировка переданного реестра; повторная подача отклонённого «в один клик» | Корректировки — следующим реестром, повторная подача — новым расходом | Пилот столкнётся с этим чаще раза в месяц |
| Аналитика и дашборды по расходам | Нужен реестр, а не BI | После Demo Day |
| Мультикомпания и онбординг новых компаний | `company_id` в схеме есть, но пользуемся одной | Вторая компания |
| Требование минимальной суммы чека | Остаётся решением владельца политики (SC-09, PRD, открытый вопрос) | Владелец политики задал порог |

## 4. Потом (порядок очереди после MVP)

1. Напоминания вне приложения (email / push).
2. Лимиты политики и их проверка.
3. Автоматическое обучение алиасов продавцов по решениям бухгалтера.
4. Редактор политики для HR.
5. Согласование руководителем.
6. Интеграция реестра с 1С / зарплатой.

## 6. Критерии готовности MVP (что показываем на Demo Day)

Числа — из [success-criteria.md](quality/success-criteria.md). «Обязательно» — то, что в MVP обязано выполняться; «Показываем замер» — измеряем честно и показываем фактическое значение, а при недостижении объясняем.

| Группа | Критерии | Статус на Demo Day |
| --- | --- | --- |
| Корректность денег и статусов (детерминированная часть) | SC-03 (100% загрузок получают финальный статус), SC-14 (категория только из справочника), SC-17 (сумма реестра сходится), SC-18, SC-19, SC-20 | **Обязательно** |
| Честность модели | Q-02 (нет выдуманных значений), Q-03 (нет выдуманных категорий), E-03 (деградация помечена) | **Обязательно** |
| Качество распознавания и категории | NS-01 ≥ 90%, NS-02 ≥ 80%, NS-03 ≤ 20%, SC-02 (паритет фото/PDF ≤ 5 п.п.), SC-04, SC-13, SC-15, Q-01 | Показываем замер |
| Скорость и цена | SC-01 / E-01 (p95 ≤ 8 с, медиана ≤ 4 с), E-02 (≤ 2 ₽ за расход) | Показываем замер |
| Время людей | NS-04 (реестр ≤ 30 мин), NS-05 (расход ≤ 60 с), SC-21 (≥ 80% понимают статус) | Показываем замер по протоколу |

Про расхождение «5 секунд» в PRD и «p95 ≤ 8 с» в Quality: пользователю обещаем «обычно до 5 секунд», а контрольная цифра — SC-01 (медиана ≤ 4 с, p95 ≤ 8 с). Это предложение Product, нужно согласие Quality.

## 8. Правила изменения скоупа

1. Скоуп меняется только PR в этот файл с пометкой «scope».
2. Новое в MVP — только если что-то равное по объёму уходит из MVP или переносится на «Потом». Просто «добавить» нельзя.
3. После **заморозки на M4** новые функции не принимаются; только дефекты.
4. Изменение скоупа, затрагивающее акторов, внешние системы или контейнеры, требует ревизии C4 и при необходимости нового ADR.
5. Каждое попадание пункта из «Не-скоупа» в MVP фиксируется строкой в журнале ниже.

## 9. Открытые вопросы, влияющие на скоуп

1. Дата Demo Day и расписание Lab 3+ — нужны, чтобы заменить ориентиры в разделе 5 датами.
2. Где проводим демо (риск 2) — решение до M2.
3. Доступ к ФНС — есть ли возможность получить к M2.
4. Срок решения для сотрудника: два числа (спорные ≤ 2 раб. дня, остальные ≤ 5) — согласовать с Quality (Q8 в [use-cases/README](use-cases/README.md)).
5. Правило периода подачи (до конца месяца покупки) — подтвердить на пилотной политике.
