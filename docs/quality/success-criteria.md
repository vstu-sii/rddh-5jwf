# Критерии успеха: Учёт расходов по чекам и выпискам

> Роль: Quality & Safety · Lab 1, Task 1 (Метрики качества)
> Сегмент: бухгалтер-аутсорсер, 2–4 ООО/ИП на УСН (см. `docs/prd.md`)
> Статус: черновые SLO финальной картинки (цель декабря), требуют sign-off Product. Числа жёсткие, валидация методом — с лабы 3.
> Принцип: каждый критерий = число + способ подсчёта. Без способа подсчёта — пожелание, а не метрика.

## 1. North Star (из PRD + способ подсчёта)

Цель: месяц сходится с фактом, спорных столько, что их не лень разобрать руками.

| ID | Формулировка | Target (жёсткий) | Способ подсчёта | Источник данных | Авто с лабы 3? |
|---|---|---|---|---|---|
| NS-01 | Доля операций, разнесённых автоматически с достаточной уверенностью | ≥ 80% | `auto_confident / total`, где `auto_confident` = операции без флага `needs_review` | Golden-месяц: 150–250 операций (выписка CSV + фото чеков + эталон категорий) | Да, скрипт |
| NS-02 | Доля спорных операций | ≤ 20% | `needs_review / total`; дополнительно абсолютный контроль ≤ 30 шт/мес на эталонном месяце | Тот же golden-месяц | Да, скрипт |
| NS-03 | Время ручного разбора одной спорной операции | ≤ 20 сек (верхняя граница PRD 15–20 сек) | Хронометраж по протоколу: открыть карточку → принять/исправить категорию → сохранить; медиана по ≥ 20 спорным | Замер вручную на стенде, протокол в `golden-dataset-plan.md` | Нет, полуавто |
| NS-04 | Расхождение суммы выписка vs разнесённые операции | ≤ 1% от оборота, каждое расхождение подсвечено | `abs(sum(categories) − sum(statement)) / turnover`; проверка флага подсветки для каждого расхождения > 0 | Golden-месяц + скрипт сверки | Да, скрипт |

Сходимость считается по итогу месяца в рублях, копейка в копейку для скрипта, допуск ≤ 1% — для бизнес-оценки (мелкие наличные без чека — отдельным флагом, а не молчаливым расхождением).

## 2. Боли PRD → что значит «решает»

### Боль 1. Пиковая разборка: пачка 30–50 фото в последний день, 2–3 часа ручной работы

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| SC-01 | Сквозное время обработки пачки 50 чеков вместе с разбором спорных | ≤ 15 мин (было 2–3 часа, экономия ≥ 85%) | Хронометраж на эталонной пачке: 50 фото (часть под углом/с пересветом) + выписка-фрагмент; старт — загрузка, финиш — категории подтверждены | Нет, замер вручную |
| SC-02 | Полнота извлечения полей с фото чека (продавец, сумма, дата, ИНН при наличии) | ≥ 95% полей без ручной правки | `correct_fields / total_fields` по разметке OCR-полей; сумма и дата — точное совпадение, продавец — нормализованное совпадение | Да, скрипт + разметка |

### Боль 2. Непрозрачное имя продавца (эквайер/агрегатор вместо «Пятёрочка»)

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| SC-03 | Точность категории Top-1 на операциях с грязным именем продавца | ≥ 90% | `correct_top1 / total_dirty`, golden-разметка категории; грязные = код эквайера/агрегатора | Да |
| SC-04 | Точность Top-2 на тех же операциях (годный кандидат в подсказке) | ≥ 95% | `top2_contains_truth / total_dirty` | Да |

### Боль 3. Один продавец — разные категории (АЗС с магазином: топливо vs канцтовары)

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| SC-05 | Точность категории на уровне позиций внутри чека | ≥ 85% | `correct_positions / total_positions` по чекам с ≥ 2 категориями в одном чеке | Да |
| SC-06 | Консистентность: повторный прогон того же кейса даёт ту же категорию | ≥ 95% | 2 прогона × golden-подмножество (n ≥ 50), `same / total` | Да |
| SC-07 | Жёсткие правила применяются детерминированно | 100% | Отдельный тест правил (fixtures «если продавец X и слово Y → категория Z»): `passed / total`, допуск только 100% | Да |

SC-07 отделяет «правила» от «привычек»: привычки меряем через SC-05/SC-06 (precision ≥ 85% без поломки SC-07).

### Боль 4. Расхождение выписки и чеков (потерян/задвоен чек, наличные без чека)

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| SC-08 | Полнота сведения: ни одна операция выписки/чека не потеряна молча | recall 100% | `matched_or_flagged / total`; каждая несопоставленная операция обязана иметь флаг (`duplicate_candidate` / `no_receipt` / `cash_no_trace`) | Да |
| SC-09 | Точность дедупликации чек ↔ выписка | precision ≥ 95% | `correct_links / predicted_links` на парах с близкой суммой/датой | Да |

Покрывается NS-04 (≤ 1%), но SC-08/SC-09 объясняют, за счёт чего: не «сошлось случайно», а «всё сопоставлено или честно помечено».

### Боль 5. Не может быстро объяснить траты клиенту («почему так много на X»)

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| SC-10 | Агрегат по категориям готов без пересчёта и сходится с фактом | 100% месяцев без ручного пересчёта перед ответом клиенту | Чек-лист на golden-месяце: открыть агрегат → сверить с NS-04 → да/нет; + время ответа ≤ 60 сек | Нет, протокол |
| SC-11 | Каждая спорная операция имеет объяснение | 100% `needs_review` содержат причину + ссылку (правило / сумма-дата / история) | Автопроверка: `has_reason_and_ref / total_review` = 100%; качество формулировок — выборочно вручную (тон: понятно бухгалтеру и клиенту, без жаргона) | Да (наличие) + вручную (тон) |

## 3. Качество ответов: точность, полнота, честность, тон

- Точность/полнота — это SC-02…SC-09 выше, дублировать не надо.
- Честность неуверенности (калибровка):

| ID | Формулировка | Target | Способ подсчёта | Авто? |
|---|---|---|---|---|
| Q-01 | Доля ошибок среди `confident` (молчалиновых неверных) | ≤ 5% | `wrong_and_confident / total_confident` | Да |
| Q-02 | Галлюцинации сумм/дат/ИНН (придуманное, чего нет в источнике) | 0 на golden-наборе | Ручная разметка + скрипт сверки с OCR/выпиской; любой случай = fail | Да (сверка) + вручную (споры) |

- Тон: для бухгалтера-аутсорсера тон = «понятно клиенту при пересылке». Отдельной шкалы 1–5 не вводим в лабе 1; контролируем через SC-11 (причина есть, без жаргона, с суммой/датой). С лабы 3 — выборочная оценка 20 объяснений, порог введём по первым замерам.

## 4. Инженерные: задержка и стоимость (цели из PRD, метод зафиксирован)

Цели внесены как цель декабря из PRD, валидация — с лабы 3 по логам. В лабе 1 обязательства выполнить нет, обязательство — считать одинаково.

| ID | Формулировка (цель PRD) | Target | Способ подсчёта (обязателен с лабы 3) |
|---|---|---|---|
| E-01 | Ответ на один чек/операцию (OCR + классификация) | p95 ≤ 5 сек | JSON-лог каждой операции: `t_total`, `t_ocr`, `t_classify`; p50/p95 скриптом по ≥ 100 операциям; пачка 50 — отдельно суммарное время (см. SC-01) |
| E-02 | Цена одной операции | ≤ 2 ₽ (ориентир PRD 1–2 ₽) | Лог токенов `in/out` по модели + тариф из `docs/model-candidates.md`: `cost = tokens_in*price_in + tokens_out*price_out`; агрегат ₽/мес на эталонном месяце 500–1000 операций |
| E-03 | Деградация при лимите/таймауте | 100% отказов помечены, 0 молчаливых | Счётчик `fallback_or_error` в логе; проверка: каждый такой кейс → `needs_review` с причиной `degraded`, а не выдуманная категория |

Формула и поля лога фиксируются здесь, чтобы AI Engineer и Delivery считали так же. Числа E-01/E-02 — из PRD, пересмотр только через ADR с ценой решения.

## 5. Что меряем автоматически с лабы 3

- Авто скриптом: NS-01, NS-02, NS-04, SC-02, SC-03, SC-04, SC-05, SC-06, SC-07, SC-08, SC-09, Q-01, Q-02 (сверка), SC-11 (наличие), E-01, E-02, E-03.
- Вручную по протоколу: NS-03 (секундомер), SC-01 (пачка), SC-10 (агрегат клиенту), тон SC-11 (выборка 20 шт).
- Judge-LLM — только второй сигнал для тона/причин; спор решает человек. Итоговая цифра — по человеку/скрипту, не по судье.

## 6. Не-цели лабы 1 и задел на golden dataset

- Не меряем: персонализацию под 4 клиентов раздельно, работу в 1С (только Excel/CSV-экспорт), рукописные чеки.
- Данные: только синтетика и обезличенные чеки; персональные данные клиентов — нельзя. Детали источников, формата записи и первые 10 примеров — в `docs/quality/golden-dataset-plan.md` (следующий шаг Quality).
- Эталонный месяц для всех подсчётов: один фиксированный набор (150–250 операций, 30–50 фото, часть грязных имён, часть мульти-категорийных чеков, 1–2 задвоения, 1–2 потери). Без фиксации набора проценты несравнимы между прогонами.

## 7. Согласование с Product

- Targets NS-01…NS-04, E-01/E-02 перенесены из `docs/prd.md` без изменений.
- Ужесточения Quality поверх PRD: SC-03 ≥ 90% (в PRD только «≥ 80% авто»), Q-01 ≤ 5%, Q-02 = 0, SC-07 = 100%, SC-08 = 100% — обоснованы ценой ошибки аутсорсера (отчётность). Требуют sign-off Product.
- Открытые вопросы PRD (доля наличных без следа; хватит ли жёстких правил без персонализации) закрываем метриками SC-08 и SC-05/SC-06 соответственно.
