# Черновик DoD команды (Lab 1) — ИСТОРИЧЕСКИЙ ДОКУМЕНТ

> **Статус: заменён.** Действующий DoD — [`dod.md`](dod.md) (Lab 2). Этот файл сохранён как история решения: в нём критерии сформулированы качественно («документ понятный», «архитектура хорошая»), без формы проверки и без блокировки мёржа. В `dod.md` каждый критерий получил одну из четырёх форм (CHECK / COUNT / REF / MANUAL) — см. §1 «Правило, по которому написан этот документ».
>
> Не используйте пороги и формулировки отсюда для приёмки: часть из них переписана.

> DoD — спека для автопроверки: что проверит judge, решаете вы. Каждый критерий проверяем: есть/нет, число, ссылка.
> Продукт: сервис компенсации расходов сотрудников (фото чека или PDF онлайн-чека → распознавание → категория → отчёт бухгалтеру).
> Требования и метрики продукта: `docs/prd.md`, `docs/quality/success-criteria.md`. Если критерий DoD расходится с порогом из `success-criteria.md`, верен `success-criteria.md`.

---

## Принципы

1. **Проверяемость** — каждый критерий даёт бинарный результат (pass/fail) или число с порогом
2. **Автоматизируемость** — то, что можно проверить скриптом/оценщиком, должно проверяться автоматически
3. **Согласованность** — DoD согласован со всей командой, изменения — только через PR с обсуждением
4. **Версионирование** — DoD версионируется вместе с кодом, тег `dod-v<YYYYMMDD>`
5. **Два входа — равные права** — критерий, прошедший на фото, обязан пройти и на PDF; расхождение фиксируется как дефект, а не как «особенность формата»

## Критерии готовности пользовательских историй (к Lab 2+)

> Эти критерии применяются к каждой US, когда команда начнёт доставку фич.
> US пишутся для каждой роли отдельно: у сотрудника и у бухгалтера разные ценности и разные приёмочные критерии для одного и того же процесса.

| Критерий | Как проверяется | Порог |
|---|---|---|
| US записана в формате: «Как <роль>, я хочу <действие>, чтобы <ценность>» | Ручной ревью PO | Да |
| Роль в US названа точно (сотрудник / бухгалтер / руководитель / HR-администратор) | Ручной ревью PO | Нет US с ролью «пользователь» без уточнения |
| Приёмочные критерии (AC) заданы в Gherkin / чек-листе | Ручной ревью | ≥1 AC на US |
| Для каждого AC есть автотест (unit / integration / e2e / eval) | CI: coverage по метке теста | 100% AC покрыты тестами |
| US проверена на обоих входах, если затрагивает распознавание | Прогон AC на фото и на PDF | Оба входа проходят, либо US явно ограничена одним входом с указанием причины |
| Golden dataset пополнен примерами под эту US | Скрипт: поиск `meta.pain_ref` / `meta.us_id` | ≥3 новых примера в датасете |
| DoD артефакта (код, промпт, пайплайн) выполнен | CI + ручной ревью | Все галочки зелёные |
| Обновлена документация (README, changelog, глоссарий если новые термины) | Ручной ревью | Да |

## Процесс согласования и изменений

1. **Инициализация** — этот черновик обсуждается на планёрке командой, правки вносятся в PR
2. **Утверждение** — после согласия всех ролей PR мёржится, ставится тег `dod-v<YYYYMMDD>`
3. **Изменения** — любое изменение DoD только через PR с ревью от Quality + минимум одной другой роли
4. **Проверка на приёмке** — на демо лабы команда показывает: «Вот наш DoD, вот чек-лист, вот что зелёное, вот что нет»

## Чек-лист для автопроверки в CI (планируемый)

```yaml
# .github/workflows/dod-check.yml (планируется к Lab 2)
name: DoD Check
on: [pull_request]
jobs:
  dod-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check repo structure
        run: python scripts/check_repo_structure.py
      - name: Validate .env.example
        run: python scripts/check_env_example.py
      - name: Validate golden dataset schema
        run: python scripts/validate_golden.py data/golden/*.jsonl schemas/golden-example.json
      - name: Check golden dataset input balance
        run: python scripts/check_golden_input_balance.py data/golden/*.jsonl
      - name: Scan golden dataset for PII patterns
        run: python scripts/check_no_pii.py data/golden/*.jsonl
      - name: Check success criteria format
        run: python scripts/check_success_criteria.py docs/quality/success-criteria.md
      - name: Word count brief.md
        run: |
          wc=$(wc -w < docs/brief.md)
          if [ $wc -gt 500 ]; then exit 1; fi
      - name: Glossary term count
        run: |
          cnt=$(grep -cE '^\| `[^`]+` \|' docs/glossary.md)
          if [ $cnt -lt 15 ]; then exit 1; fi
```

## Открытые вопросы (к согласованию на планёрке)

1. **Порог автотестов** — требуем ли 100% coverage по AC с первой US или вводим постепенно?
2. **Глоссарий** — 15 терминов минимум или больше? Кто валидирует определения (Product или вся команда)?
3. **Golden dataset** — валидируем ли схему на CI с Lab 1 или ждём Lab 2?
4. **ADR** — обязателен ли ADR на каждое архитектурное решение или только на ключевые (OCR-движок, модель, способ хранения оригиналов чеков)?
5. **Deploy URL** — считаем ли hello-world «продом» или нужен отдельный staging?
6. **Смешанный чек** — считаем ли один расход с двумя категориями одной записью или двумя? От этого зависит формат golden-записи и правило SC-13.
7. **Оригиналы чеков в тестовых данных** — храним ли реальные обезличенные изображения в репозитории или только ссылки на защищённое хранилище?
