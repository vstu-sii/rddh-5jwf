# Golden dataset v1

> Роль-владелец: Quality & Safety. Набор написан **до кода** — прямо из use cases и болей PRD, чтобы метрика не подгонялась под то, что система случайно научилась делать.

## Что здесь лежит

| Файл | Что это |
|---|---|
| [`v1.jsonl`](v1.jsonl) | **Сам набор**: 45 записей «вход → эталон», одна запись на строку |
| [`categories.txt`](categories.txt) | Справочник категорий политики — источник для проверки, что модель не выдумывает категории |
| [`inbox/`](inbox/) | Сюда кладутся новые примеры до приёмки (см. процесс ниже) |

Схема записи: [`schemas/golden-example.json`](../../../schemas/golden-example.json).
Валидатор: [`scripts/quality/check_golden.py`](../../../scripts/quality/check_golden.py).

## Формат: почему JSONL и почему такой

**JSONL, а не CSV и не xlsx.** Каждая строка — самостоятельный JSON-объект. Это даёт три вещи, важные именно для evals:

1. **Диф по строкам в git.** Видно, какая именно запись изменилась, — а не «файл пересохранён целиком».
2. **Потоковое чтение.** Набор можно скормить инструменту evals без загрузки в память и разворачивать в батчи.
3. **Вложенность без боли.** У записи есть `input.items[]` и `meta.expected_context[]` — в плоской таблице это пришлось бы разносить по нескольким листам.

**Читается существующими инструментами.** Формат — обычный JSONL, поэтому набор едет и в `openai/evals`, и в `promptfoo`, и в собственный раннер `scripts/quality/run_evals.py`. Ничего экзотического: одна строка — один JSON.

**Кейсы на контекст, а не только на итоговый текст.** Это требование шага спринта, и в записи оно выражено полем `meta.expected_context`:

```json
"meta": {
  "expected_context": ["policy.company_01.education"],
  "injected_text": "..."
}
```

`expected_context` перечисляет документы политики, на которые ответ **обязан** опираться. Проверяется это так: раннер убирает указанный документ из контекста и смотрит, изменился ли ответ. Если ответ не изменился — модель его не использовала, и это фиксируется как провал, даже когда итоговая категория совпала. Без этого поля «правильный ответ» невозможно отличить от «угадал».

## Разметка болей: `pain_ref` против `scenario_ref`

Набор проверяет слой «чек → категория → вердикт», и не всё, что он проверяет, является болью PRD. Поэтому разметка разделена на два поля:

| Поле | Что означает | Значения |
|---|---|---|
| `pain_ref` | Боль из `docs/prd.md`, **номер которой совпадает с номером боли в PRD** | 1 — качество фото (11), 2 — формат PDF (10), 3 — неясна компенсируемость (22) |
| `scenario_ref` | Сценарий, который набор проверяет, но который **не является** болью PRD | `scenario_mixed_receipt` (4), `scenario_duplicate_expense` (2), `scenario_prompt_injection` (2), `scenario_contested_category` (1) |

**Почему разделено.** В первой редакции набора девять записей были помечены `pain_4_contested_category`. Это ошибка: в PRD **боль 4 — «дедлайн подачи легко пропустить»**, а не спорная категория. Номер боли был приписан содержанию, к которому он не относится, и трассировка «боль PRD → записи набора» стала ложной.

Валидатор теперь ловит это: `pain_ref` ограничен пятью реальными болями PRD (`enum` в схеме), а сценарии вроде инъекции или дубля помечаются отдельным полем. Проверка `Q-08` и `pains` в `check_golden.py` падают, если номер боли не соответствует содержанию.

**Честный пробел в покрытии.** Боли PRD **4 (дедлайн)** и **5 (видимость статуса)** набором **не покрыты — 0 записей**. Это осознанно: они относятся к UX-слою (напоминания, отображение статуса), а не к слою распознавания и категоризации, который проверяет golden dataset. Их измеряют `SC-09` и `SC-21` из `docs/quality/success-criteria.md`. Провалом набора это не является, но и не замалчивается: проверка `pains` печатает «покрыты боли PRD [1, 2, 3]».

## Состав набора

45 записей, 8 use cases, 7 типов краевых случаев.

| Разрез | Значение |
|---|---|
| Записей | 45 |
| Входы (после разворота `mixed_batch`) | `receipt_photo` 28 (57%), `receipt_pdf` 21 (43%) |
| Use cases | UC-01 = 12, UC-02 = 7, UC-03 = 4, UC-04 = 6, UC-05 = 6, UC-06 = 3, UC-07 = 3, UC-08 = 4 |
| Краевые случаи | `non_reimbursable_category` 9, `mixed_receipt` 4, `unreadable_photo` 4, `unknown_merchant` 3, `duplicate` 2, `no_receipt` 2, `pdf_no_text_layer` 2 |
| Инъекции (LLM01) | 3 записи (gs-020, gs-021, gs-046) с полем `injected_text` |
| Записи-повторы (SC-15) | 4 (gs-033, gs-034, gs-035, gs-045) |
| Компании | `company_01` (41), `company_02` (4) |

**Про баланс входов.** Нижняя граница 30% на каждый вход выбрана не произвольно: при 45 записях это 14 записей на подмножество, и разница в 5 п.п. (порог SC-02) на таком объёме ещё различима, а не выведена из шума. Фактически получилось 43% / 57% — запас на случай, если часть записей выпадет при развороте.

**Про `company_02`.** Четыре записи на второй компании нужны, чтобы поймать ошибку, которую невозможно заметить на одной политике: категория, верная для `company_01`, неверна для `company_02`. Это проверка SC-14 — категория обязана принадлежать справочнику конкретной компании.

## Почему 45, а не «побольше»

Задача лабы 2 — 30–50 записей. Верхняя граница тоже осмысленна: набор, который никто не поддерживает, деградирует быстрее, чем маленький, но живой. 45 записей покрывают все 8 UC минимум тремя кейсами и все обязательные краевые случаи — при этом набор реально прочитывается одним человеком за один присест, и это условие его дальнейшей жизни.

## Владелец и процесс пополнения

| Роль | Ответственность |
|---|---|
| **Quality & Safety** | Владелец: формат, версионирование, приёмка, запуск evals, решение о выпуске версии |
| **Product / VO** | Приносит живые примеры из интервью; подтверждает, что UC покрыт |
| **AI Engineer** | Приносит примеры из ошибок прогонов (`false_positive` / `false_negative`) — самый ценный источник |
| **Бухгалтер-респондент** | Подтверждает вердикт `reimbursable` под политику своей компании |

### Процесс: как пример попадает в набор

1. **Положить в `inbox/`.** Файл `inbox/<source>_<date>.jsonl`, те же поля, что в основной набор.
2. **Прогнать валидатор.** `python scripts/quality/check_golden.py docs/quality/golden-dataset/inbox/*.jsonl`. Красный результат — пример не принят, причина видна в выводе.
3. **Проверить глазами:** нет ли PII, есть ли `meta.uc_id`, обоснован ли `notes` при `reference.confidence < 0.9`.
4. **Смержить в `v1.jsonl`** (или в `v2.jsonl` — см. версионирование ниже) и убедиться, что `check_golden.py` остаётся зелёным.
5. **Зафиксировать тег** `golden-dataset-v<YYYYMMDD>`.

### Правило пополнения: пример из ошибки важнее примера из фантазии

Приоритет источников, от лучшего к худшему:

1. **Реальная ошибка прогона** — система ошиблась, эталон исправлен руками. Такой пример прицельно закрывает известную дыру.
2. **Реальный обезличенный чек** от респондента — проверяет, что набор не оторван от жизни.
3. **Синтетика по шаблону** — нужна для систематического покрытия (все краевые случаи × оба входа), но сама по себе ничего не доказывает.

Набор v1 — в основном синтетика: интервью Lab 1 не дали выгрузки реальных чеков. Это **осознанное ограничение**, и оно записано честно (см. `docs/quality/experiments/lab2-prompt-on-golden.md`): синтетика проверяет логику конвейера, но не доказывает качество на настоящих термочеках. Первые реальные чеки — задача лабы 3.

## Версионирование

- Набор версионируется файлом: `v1.jsonl` → `v2.jsonl`. **Записи из старой версии не переписываются** — иначе метрика между прогонами становится несравнима.
- Удаление записи (например, отзыв согласия) фиксируется в [`CHANGELOG.md`](CHANGELOG.md) фактом удаления без содержания.
- Тег в git: `golden-dataset-v<YYYYMMDD>`.
