# Definition of Done: артефакты команды (Lab 2)

> Роль-владелец: Quality & Safety. Согласуется с Product и командой **до** начала стройки (шаг 1 спринта 2).
> Заменяет черновик [`dod-draft.md`](dod-draft.md) — тот остаётся историей Lab 1.

## Правило, по которому написан этот документ

**Критерий DoD либо проверяем машиной, либо переписывается.** Формулировка «код качественный», «документ понятный», «архитектура хорошая» не является критерием: её нельзя превратить в pass/fail без вкусовщины. Каждый критерий ниже имеет одну из четырёх форм:

| Форма | Что значит | Пример |
|---|---|---|
| **CHECK** | исполняемая проверка в CI, есть скрипт, exit code ≠ 0 = fail | `scripts/quality/check_golden.py` |
| **COUNT** | число с порогом, считается скриптом | «≥ 30 записей в golden-наборе» |
| **REF** | критерий = существование артефакта по ссылке из этого документа | «ADR-0001 существует и датирован» |
| **MANUAL** | человек по протоколу, протокол описан здесь же; **не более 20% критериев** | хронометраж NS-04 |

Введена четвёртая форма осознанно: часть работы (интервью, замер секундомером, приёмка тона объяснений) машинно не проверяется, и делать вид, что проверяется, — хуже, чем назвать это честно. Но у каждой MANUAL-проверки есть протокол (кто, сколько раз, что считается провалом), иначе она превращается в «посмотрели, вроде норм». Доля MANUAL ограничена 20% — если её превысить, DoD перестаёт быть спекой для автопроверки и становится пожеланием.

**Столбец «Блок»** отвечает на вопрос «что именно блокирует мёрж»: `merge` — красный CI, `demo` — показывается на приёмке, `later` — вступает в силу с лабы 3+.

## 0. Как этот DoD проверяется целиком

Один вход, один exit code:

```bash
python scripts/quality/check_dod.py            # локально
python scripts/quality/check_dod.py --ci       # в CI: только CHECK-критерии
python scripts/quality/check_dod.py --json     # машинный отчёт для жюри
```

Скрипт печатает таблицу `ID | критерий | форма | результат | деталь` и возвращает `1`, если провален хотя бы один `merge`-критерий формы CHECK или COUNT. Это и есть точка стыковки DoD с автопроверкой: жюри не читает документ, а запускает скрипт.

## 1. Продуктовые артефакты — владелец Product / VO

| ID | Критерий | Форма | Как проверяется | Порог | Блок |
|---|---|---|---|---|---|
| P-01 | PRD существует и назван конкретно | CHECK | `check_dod.py`: файл есть, секции «Сегмент», «Боли», «North Star» присутствуют | 3/3 секции | merge |
| P-02 | Use cases проживаются: 4–6 UC с основным и альтернативным потоком | COUNT | счёт UC-секций в `docs/use-cases.md` | ≥ 4 UC, у каждого ≥ 1 alt-поток | merge |
| P-03 | Каждый UC трассируется на боль PRD | CHECK | у каждой UC-секции есть ссылка `Боль N` или `pain_N` | 100% UC | merge |
| P-04 | Каждый UC покрыт ≥ 3 записями golden dataset | CHECK | `check_golden.py --uc-coverage`: `meta.uc_id` каждой UC | ≥ 3 записи на UC | merge |
| P-05 | Глоссарий согласован (снята пометка «не финализирован») | MANUAL | протокол ниже | пометка снята, ≥ 15 терминов | demo |
| P-06 | Гипотезы фальсифицируемы | CHECK | у каждой H-секции есть «Это неверно, если» | 100% гипотез | merge |
| P-07 | Политика компенсации — справочник, а не текст в промпте | REF | `database/schema.sql`: таблица `expense_category` с `company_id` | таблица есть | demo |

**Протокол P-05 (MANUAL).** Владелец: Product. Проверка: на планёрке Product зачитывает 5 случайных терминов, команда формулирует определение своими словами. Провал: расхождение формулировок между ролями; термин переписывается. Повтор до нуля расхождений. Исполнитель фиксирует результат строкой в PR.

## 2. AI / ML артефакты — владелец AI Engineer

| ID | Критерий | Форма | Как проверяется | Порог | Блок |
|---|---|---|---|---|---|
| A-01 | Ресёрч с проверяемыми источниками | COUNT | счёт уникальных `http(s)://` ссылок в `docs/research.md` | ≥ 8 ссылок | merge |
| A-02 | Кандидаты моделей с ценой за сценарий | CHECK | `check_dod.py`: таблица в `docs/model-candidates.md` содержит колонку цены и ≥ 2 кандидата | ≥ 2 кандидата | merge |
| A-03 | Промпт — артефакт в репозитории с версией | REF | файл `prompts/categorize.v<N>.md` существует | файл есть | demo |
| A-04 | Строгая JSON-схема ответа модели | CHECK | `check_dod.py`: файл `schemas/llm-categorize.json` валиден как JSON Schema | схема валидна | merge |
| A-05 | Ответ модели валидируется схемой, а не принимается на веру | CHECK | `pytest tests/test_llm_adapter.py` — тест на невалидный ответ падает в `degraded`, а не в категорию | тест зелёный | merge |
| A-06 | Точность категории на golden-наборе измерена | CHECK | `scripts/quality/run_evals.py` на golden v1 | отчёт с числом, не «работает» | later |
| A-07 | Честная записка об экспериментах Lab 1 сохранена | REF | `docs/experiments/lab1.md` существует | файл есть | demo |

**Про A-06.** В лабе 2 метрика ещё не обязана пройти порог NS-02 (≥ 80%) — обязательство лабы 2 в том, что **прогон существует и число записано честно**, включая провал. Порог становится блокирующим с лабы 3. Это разделение принципиально: если требовать зелёную метрику до того, как построен пайплайн, команда начнёт подгонять набор под результат.

## 3. Инженерные артефакты — владелец Delivery

| ID | Критерий | Форма | Как проверяется | Порог | Блок |

| D-02 | C4 соответствует compose | CHECK | `aact diff ... --current-format compose`, расхождения только из белого списка | 0 необъявленных | merge |

| D-07 | У каждого ADR есть цена решения | CHECK | в каждом ADR есть секция «Цена решения» / «Последствия» | 100% ADR | merge |
| D-08 | Прод отвечает | CHECK | `curl -fsS <URL>/health` | HTTP 200, < 5 с | demo |
| D-09 | Структура репозитория совпадает с README | CHECK | `check_repo_structure.py` | 0 отклонений | demo |
| D-10 | Секретов нет в репозитории | CHECK | `check_no_secrets.py` по дереву и `.env.example` | 0 находок | merge |

**Про D-02.** `aact diff` показывает три ожидаемых расхождения: люди и внешние системы (их нет в compose), и связь `llm_adapter → llm_runtime` (Ollama поднимается только профилем `local-llm`). Скрипт считает их известными; **любое новое расхождение — fail**. Белый список живёт в `scripts/quality/check_dod.py` рядом с проверкой, чтобы его нельзя было расширить незаметно в другом файле.

## 5. Границы: что в этот DoD не входит

Названо явно, чтобы «не сделано» не путали с «забыли описать»:

- **Персонализация политики по отделам**, интеграция с 1С, рукописные чеки, валютные расходы, многостраничные PDF-выписки — не-цели Lab 1 (`success-criteria.md`), остаются не-целями Lab 2.
- **Нагрузочное тестирование** — не входит: объём 1–5 тыс. чеков/мес на компанию не создаёт нагрузки, требующей отдельного контура.
- **Пентест внешним подрядчиком** — не входит; атаки лабы 4 выполняет команда по списку Q-14.
- **Юридическая экспертиза политики компенсации** — вне зоны качества; эталонный вердикт подтверждает бухгалтер-респондент.

## 6. Согласование

DoD считается действующим, когда выполнены три условия:

1. **Product** подтверждает формулировки P-01…P-07 и не оспаривает пороги метрик, унаследованные из PRD (`success-criteria.md` §7).
2. **AI Engineer** подтверждает A-01…A-05 и согласен, что A-06 в лабе 2 требует записи числа, а не достижения порога.
3. **Delivery** подтверждает D-01…D-10 и что список известных расхождений `aact diff` (D-02) полон.

Правки — только через PR к этому файлу с ревью Quality и минимум одной другой роли. Изменение любого порога фиксируется строкой в таблице версий ниже с указанием причины.

| Версия | Дата | Автор | Изменение |
|---|---|---|---|
| dod-v20261015 | 2026-10-15 | Quality & Safety | Первая редакция Lab 2: 4 формы критериев, блокирующие CHECK/COUNT, протоколы MANUAL, границы |

**Статус согласования:** вынесен на планёрку Lab 2.

## 7. Текущее состояние проверки

Вывод `python scripts/quality/check_dod.py` на момент PR:

| Показатель | Значение |
|---|---|
| Всего критериев | 31 |
| PASS | 27 |
| FAIL | 0 |
| SKIP (ручная проверка) | 4 |

Четыре SKIP — это **не провалы**, а критерии, которые машиной не проверяются by design:

| ID | Критерий | Почему SKIP | Что осталось сделать |
|---|---|---|---|
| P-05 | Глоссарий согласован | MANUAL: нужен устный прогон на планёрке | Product снимает пометку «не финализирован» после обсуждения |
| A-06 | Точность категории на golden | Порог становится блокирующим с лабы 3 | Прогон на реальной модели, а не на baseline |
| Q-12 | Требование регулятора | MANUAL: формулируется человеком | §5 `threat-model.md` уже содержит требование; подтвердить на приёмке |
| Q-13 | Рискованное допущение проверено | MANUAL + результат уже есть | Записка `experiments/lab2-prompt-on-golden.md` фиксирует, что допущение **не подтвердилось** |

**Как воспроизвести:**

```bash
python scripts/quality/check_dod.py            # 27 PASS / 0 FAIL / 4 SKIP
python scripts/quality/check_golden.py docs/quality/golden-dataset/v1.jsonl
```

**Что показал прогон (кратко).** Эксперимент Q-13 дал три результата, которые входят в лабу 3 как задачи: (1) допущение лабы 1 «100% на 6 кейсах» не масштабируется на 45 кейсов — точность ровно на пороге NS-02; (2) prompt injection расширил права в 1 случае из 3 — ущерб ограничил архитектурный барьер, а не промпт; (3) флаг ручной проверки 0.82 при пороге 0.95 — `needs_review` должен собираться из нескольких слоёв, а не быть ответственностью классификатора. Детали и числа — в [`experiments/lab2-prompt-on-golden.md`](experiments/lab2-prompt-on-golden.md).
