# ADR-0001: Распознавание чека — асинхронный конвейер через очередь

- **Статус:** предложено (Delivery), на приёмке у Product
- **Дата:** 2026-10-15
- **Затрагивает:** `api`, `task_queue`, `recognition_worker`, `ocr_service`, `llm_adapter`, `fns_adapter` — [C4 Container](../architecture/c4-container.puml)

## Контекст

Распознавание одного чека — это цепочка шагов разной длительности: QR → реквизиты ФНС, текст PDF или OCR фото, извлечение полей, категоризация локальной LLM, проверка JSON-схемы ответа. OCR (PaddleOCR) и локальная Qwen2.5-7B — тяжёлые по CPU/GPU и памяти; облачный резерв и API ФНС — внешние и могут отвечать медленно или с ошибкой.

Требования: распознавание ≤ 5 с (PRD), p95 ≤ 8 с от приёма файла до показа полей (SC-01, E-01); 100% загрузок получают финальный статус, ни одна не теряется молча (SC-03, E-03).

## Решение

`api` принимает файл, передаёт его `expense_store`, ставит задачу в `task_queue` (Redis) и сразу отвечает `202` со статусом `processing`. Отдельный `recognition_worker` забирает задачу, вызывает `ocr_service`, `fns_adapter`, `llm_adapter` и сохраняет результат и метрики прогона (`recognition_run`) через `expense_store`. Клиент узнаёт результат опросом статуса расхода.

## Альтернативы

| Вариант | Почему не берём |
| --- | --- |
| Синхронно внутри HTTP-запроса `api` | Тяжёлый OCR/LLM держит воркеры API; таймаут или падение модели = потерянная загрузка без статуса (нарушает SC-03). Нельзя масштабировать распознавание отдельно от API. |
| OCR и LLM как библиотеки внутри `api` | Раздувает образ API зависимостями PaddleOCR и весами модели, смешивает доменную логику с инференсом. |
| Брокер Kafka/RabbitMQ | Избыточно для 1–5 тыс. чеков в месяц на компанию (PRD); Redis уже даёт очередь с ретраями. |

## Цена решения

- **Eventual consistency:** между загрузкой и готовыми полями есть окно `processing`. Клиенту нужен опрос (или позже — push); экран «распознаём» обязателен в UI.
- **Ещё один компонент эксплуатации** — Redis: мониторинг, persistence (`appendonly`), поведение при рестарте.
- **Бюджет 5 с делится между очередью и шагами.** Задержка ожидания в очереди входит в SC-01; `t_total` в `recognition_run` должен считать время от приёма файла, а не от взятия задачи, иначе метрика обманет.
- **Идемпотентность обязательна:** задача может выполниться дважды (ретрай после падения worker) — сохранение результата должно перезаписывать, а не дублировать.

## Последствия

- Деградация (лимит бюджета LLM, недоступность ФНС, низкий confidence OCR) — это не ошибка запроса, а статус расхода с причиной (`degraded`, `needs_review`).
- Масштабирование: число `recognition_worker` растёт независимо от `api`.
