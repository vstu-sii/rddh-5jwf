# ADR-0002: Единственный владелец данных — сервис `expense_store`

- **Статус:** предложено (Delivery), на приёмке у Product
- **Дата:** 2026-10-15
- **Затрагивает:** `expense_store`, `expense_db`, `receipt_files`, `api`, `recognition_worker` — [C4 Container](../architecture/c4-container.puml), [schema.sql](../../database/schema.sql)

## Контекст

Писать данные нужны двум сервисам: `api` (заявки, решения бухгалтера, реестр) и `recognition_worker` (результаты распознавания, позиции чека, метрики прогона). Данные — деньги и налоговое основание: сумма реестра должна сходиться с включёнными расходами копейка в копейку (SC-17), у каждой смены статуса — запись с временем и актором (SC-20).

Если оба сервиса пишут в одну БД напрямую, инварианты (статусная машина, сумма реестра, дедупликация по ФН/ФД/ФП) размазываются по двум кодовым базам, а схема становится общей точкой связанности. Это проверяемо: aact-правила `crud` и `dbPerService` такую схему отклоняют.

## Решение

Только `expense_store` (тег `repo`) ходит в `expense_db` (PostgreSQL) и `receipt_files` (S3-совместимое хранилище, SeaweedFS). Остальные сервисы работают с данными через его HTTP API. Инварианты, которые нельзя нарушить ни одним клиентом, дублируются ограничениями БД (`CHECK`, уникальные индексы) — см. `schema.sql`.

Правило закреплено в двух местах: в C4 (проверяет `aact check`) и в сетях compose — к сети `data` подключён только `expense_store`, у `api` имя `expense_db` даже не резолвится.

## Альтернативы

| Вариант | Почему не берём |
| --- | --- |
| `api` и worker пишут в БД напрямую | Общая схема, инварианты в двух местах; нарушает `crud` и `dbPerService`. |
| Worker пишет результат через `api` | `api` становится владельцем данных и одновременно доменным сервисом с очередью — смешение ролей; появляется цикл зависимостей при обратном вызове. |
| Отдельный repo-сервис на каждое хранилище | Для MVP лишний сервис: оба хранилища описывают одну сущность «расход с документом». |

## Цена решения

- **Лишний сетевой переход** на каждое чтение и запись: `api → expense_store → БД`. Для бюджета 5 с это миллисекунды, но это ещё один процесс, который может упасть.
- **Ещё один сервис в эксплуатации и в CI** — со своим API-контрактом, который нужно версионировать вместе с `api/openapi.yaml`.
- **Транзакции через границу сервиса невозможны:** «записать файл в S3 + строку в БД» внутри `expense_store` — сначала объект, потом строка; висячие объекты без строки чистит периодическая задача.
- **Отчёты и аналитика** не могут читать БД напрямую — нужен эндпоинт в `expense_store` или отдельная read-реплика по отдельному ADR.
